# CharLine 认证方案总结：JWT + Ed25519 私钥签名

本文档总结 CharLine 在 **client-server 架构**下采用  
**JWT + Ed25519 私钥签名（Proof of Possession）** 的认证方案设计、完整流程以及关键疑问的统一结论。

---

## 一、为什么仅使用 JWT 不够安全

### 1. JWT 的本质
JWT 属于 **Bearer Token**：

> 谁持有 token，谁就被视为合法用户。

### 2. 明确风险
在以下条件下：

- token 无过期
- token 存储在客户端本地文件
- server 无 session / 无用户状态

一旦 token 泄露：

- 攻击者可永久伪装用户
- server 无法区分真假客户端
- 只能通过 **整体失效（换密钥 / bump 版本）** 解决

**结论：仅 JWT 不满足长期安全需求。**

---

## 二、引入 Ed25519 的核心目标

一句话总结：

> **让“我是谁”与“我是否仍持有私钥”强绑定**

通过非对称加密实现：

- token 只表示身份声明
- 私钥才是真正的登录凭证

---

## 三、整体方案概览

```
JWT：声明身份（uid, version）
Ed25519 私钥：证明“我就是这个身份的拥有者”
Nonce：防止签名被重放
```

---

## 四、Join 阶段（首次加入）

### 4.1 是否由 client 生成密钥对？

**必须由 client 生成。**

原因：
- 私钥不应通过网络传输
- server 不应保存私钥
- client 才能证明身份连续性

### 4.2 Join 流程

1. client 本地生成 Ed25519 密钥对
2. 私钥仅保存本地
3. 公钥随 join 请求发送给 server
4. server 绑定 `username → pubkey`
5. server 签发 JWT（无过期）

---

## 五、登录 / 鉴权流程（重点）

### 5.1 为什么需要 challenge（nonce）

目的：**防止重放攻击（Replay Attack）**

如果没有 nonce：

- 攻击者抓包后可无限重放签名请求
- 非对称签名失效

### 5.2 标准流程

1. server 下发随机 nonce
2. client 使用私钥对 nonce 签名
3. client 发送 `{ token, nonce, signature }`
4. server：
   - 验 JWT
   - 取公钥
   - 验签
   - 校验 nonce 是否有效且未使用

## 六、Nonce 设计结论

| 项目 | 结论 |
|----|----|
| 是否永久 | 否 |
| 生命周期 | 5～30 秒 |
| 是否可复用 | 否（一次性） |
| 存储位置 | server 内存 |
| server 重启 | nonce 全部失效（可接受） |

**允许 server 持有极少量短期内存状态，不违背无状态原则。**

---

## 七、Token 泄露后的安全性分析

| 泄露内容 | 后果 |
|--------|------|
| JWT token | ❌ 无法登录（缺私钥） |
| 公钥 | ❌ 无风险 |
| 私钥 | ❌ 账号完全失控 |
| 私钥 + token | ❌ 等同账号被盗 |

> 私钥 = 身份  
> token = 声明

---

## 八、客户端本地文件布局与创建机制

### 8.1 文件是否随打包存在？

**不会。**

打包后只有一个可执行文件。

### 8.2 目录创建时机

- 在 client 启动时创建
- 若不存在则自动生成

### 8.3 推荐目录结构

```
~/.charline/   （Linux/macOS）
│
├── id_ed25519         # 私钥（600）
├── id_ed25519.pub     # 公钥
├── token.jwt          # JWT
├── config.json        # 用户配置
└── charline.db        # SQLite 聊天记录
```

Windows 建议使用：

```
os.UserConfigDir()/charline
```

## 九、是否仍需要邀请码？

| 场景 | 是否需要 |
|----|----|
| 首次加入 | 是 |
| 同设备重连 | 否 |
| 新设备（复制私钥） | 否 |
| 私钥丢失 | 是 |

> 邀请码 ≈ 创建身份  
> 私钥 ≈ 维持身份

---

## 十、方案优缺点总结

### 优点
- token 泄露风险大幅降低
- server 无需保存私钥
- server 无长期状态
- 非常适合 CLI 工具

### 代价
- 实现复杂度中等
- 用户需理解“私钥即身份”
- 私钥丢失不可恢复（设计如此）

---

## 十一、最终结论（明确）

> **CharLine 推荐使用：JWT + Ed25519 私钥签名（PoP）方案**

这是一个在 **安全性、实现复杂度、CLI 使用体验** 之间平衡最优的方案，  
尤其适合：**邀请制、无中心存储、终端聊天系统**。
